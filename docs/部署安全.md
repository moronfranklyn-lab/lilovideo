# 部署安全

> 本文说明为什么底座的配置方式不能直接上公网，以及现在如何防护。

---

## 1. 问题

底座的原始设计是**本地单用户工具**：用户在网页上填自己的 API Key，写进 `config.yaml`。
本机使用时这完全合理。

但部署到公网后，它变成两个真实漏洞：

| 漏洞 | 说明 | 后果 |
| --- | --- | --- |
| **写接口无鉴权** | `PUT /api/config` 任何人可调 | 攻击者可覆盖你的密钥配置 |
| **`base_url` 可改** | 该接口接受任意 `base_url` | **攻击者把接口地址指向自己的服务器，之后所有模型请求连同 API Key 都会发到那里** |

第二条是最严重的：它不只是"改配置"，而是**直接窃取密钥**。

此外，配置接口本身零鉴权（`api/app.py`、`api/dependencies.py` 中没有任何鉴权中间件）。

---

## 2. 防护设计

采用两道防线，**互为补充**。

### 防线一（主）：环境变量优先

线上部署时密钥只放在**服务端环境变量**里，不存在于可写文件。这样即使攻击者
改写了 `config.yaml`，也拿不到有效密钥。

支持的变量：

| 环境变量 | 对应配置 |
| --- | --- |
| `DASHSCOPE_API_KEY` | `api_providers.dashscope.api_key` |
| `ARK_API_KEY` | `api_providers.ark.api_key` |
| `OPENAI_API_KEY` | `api_providers.openai.api_key` |
| `GEMINI_API_KEY` | `api_providers.gemini.api_key` |
| `DEEPSEEK_API_KEY` | `api_providers.deepseek.api_key` |
| `KLING_ACCESS_KEY` / `KLING_SECRET_KEY` | `api_providers.kling.*` |

**关键实现细节**：写配置时，由环境变量提供的密钥会被**从落盘副本中剥离**，
真实值只保留在内存。否则一次配置写入就把密钥写回了文件，防线一失效。

同时，`update_config` 在写入后**重新套用环境变量覆盖**，攻击者无法通过
写配置来覆盖内存中的密钥。

### 防线二（辅）：按监听地址自动判定模式

| 监听地址 | 模式 | 网页改配置 |
| --- | --- | --- |
| `127.0.0.1` / `localhost` / `::1` | `local` | 允许 |
| `0.0.0.0` 或具体外部地址 / 空值 | `public` | **禁止，返回 403** |

**为什么按监听地址自动判定**：默认行为完全不变（本地开发照旧），而一旦为了
对外访问改成监听 `0.0.0.0`，防护**自动生效**——不依赖使用者记得改开关。

空值按 `public` 处理是刻意的：拿不到确定信息时选择更安全的判定。

### 响应脱敏

所有配置响应统一走脱敏，密钥字段只回 `********`（固定长度，不泄漏密钥长度或片段）。
本地模式下也脱敏——没有理由把密钥回显给浏览器。

## 3. 上线部署方式

**不要在公网服务器上创建 `config.yaml` 填密钥。** 用环境变量：

```bash
export DASHSCOPE_API_KEY="你的通义密钥"
export ARK_API_KEY="你的火山方舟密钥"

cd src/backend
.venv/bin/python api_server.py
```

启动后访问 `GET /api/config`，应看到：

```json
{
  "mode": "public",
  "config_writable": false,
  "config": {
    "api_providers": {
      "ark": { "api_key": "********" }
    }
  }
}
```

界面上的「设置」页会自动变为**只读**：输入框禁用、保存按钮隐藏、顶部显示说明。

## 4. 实测证据

### 公网模式（模拟监听 0.0.0.0）

| 验证项 | 结果 |
| --- | --- |
| `GET /api/config` 报告模式 | `mode: public`、`config_writable: false` |
| 密钥是否泄漏 | 返回 `'********'`，原始响应扫描真密钥 **0 处命中** |
| `PUT /api/config` | **HTTP 403**，拒绝 |
| 攻击者的 `base_url` 是否被写入 | **0 次命中**，未生效 |

### 本地模式（回归验证）

| 验证项 | 结果 |
| --- | --- |
| 健康检查 | 正常 |
| `mode` / `config_writable` | `local` / `true` |
| 密钥仍脱敏 | 是 |
| `PUT /api/config` | HTTP 200，开发不受影响 |
| 用户自填的密钥是否被误清 | **未清空**（长度 116 / 46 位均保留） |
| 设置页输入可用性 | 36 个输入全部可编辑，保存按钮存在，无警告 |

## 5. 测试

`tests/test_deployment.py`，**24 个用例**，覆盖：

- 模式判定（含空值、大小写、带空格）
- 脱敏不泄漏长度与片段、不修改原配置
- 环境变量覆盖优先级、空字符串视为未设置
- **环境变量提供的密钥不落盘**
- **用户自填的密钥不被误清**
- **写盘与内存分离的完整流程**（攻击者写入的值既不落盘也不覆盖环境变量）

全量测试：**57 passed**。

## 6. 仍未覆盖的范围（重要）

本文只解决了「配置与密钥」层面的问题。**上架公网前还需要以下工作**，
它们不在本次范围内：

| 未覆盖 | 说明 |
| --- | --- |
| **账号与鉴权** | 当前所有业务接口无鉴权，任何人可调用并消耗你的模型额度 |
| **多租户隔离** | 任何人都能读到别人的会话与产物 |
| **配额与限流** | 无额度控制，被刷会产生真实费用 |
| **内容审核** | 无输入输出审核，公网 AIGC 有合规风险 |
| **计费** | 无付费与账务 |

也就是说：**本次修复挡的是"密钥被窃取"，不挡"额度被刷光"。**
后者需要账号体系，属于后续阶段的工作。
