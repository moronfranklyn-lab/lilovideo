## 1. 目标用户与核心任务

### 1.1 目标用户

**主要用户：个人内容创作者**

做短视频、短剧、带货视频的个人创作者。他们通常一个人完成从创意到成片的全部工作，没有编剧、没有分镜师、没有剪辑师。

**次要用户：企业内容团队**

MCN 机构、品牌市场部、广告代理、教育培训机构的视频制作团队，需要批量产出风格统一的视频。

### 1.2 使用场景

创作者手里有一个想法，可能是一句话、一段梗概，或者一个模糊的画面感。他知道要拍什么，但把想法变成成片之间隔着一长串专业工作：写剧本、定角色、画分镜、做参考图、生成镜头、剪辑配乐。

他现在的选择都不理想：

| 现有做法 | 问题 |
| --- | --- |
| 用文生视频工具直接生成 | 出来的是零散片段，角色不一致、镜头接不上，还要自己剪 |
| 自己一步步用各种 AI 工具拼 | 工具之间不衔接，中间产物要手工搬运，改一处要全部重做 |
| 找外包团队 | 周期长、成本高，不适合快速试错 |

### 1.3 核心任务

**把一句话创意，变成一部可以直接发布的成片。**

用户负责创意和判断，系统负责中间的调度、连贯性和返工。

### 1.4 核心痛点

1. **不可控**：文生视频是黑盒，出来的东西不对只能重抽。
2. **返工贵**：改一个角色，所有镜头都要重做。
3. **不连贯**：角色、场景在不同镜头里对不上。
4. **成本不可见**：视频按秒计费，生成前不知道要花多少，生成后才发现超了。

## 2. 输入、过程和产物

### 2.1 输入

| 输入 | 必填 | 说明 |
| --- | --- | --- |
| 创意描述 | 是 | 一句话想法或一段梗概 |
| 篇幅设定 | 否 | 集数、每集时长；不填则用默认值 |
| 风格 | 否 | 写实、动漫、水墨等；不填则用默认值 |
| 画面比例 | 否 | 横屏 16:9 / 竖屏 9:16 |
| 参考素材 | 否 | 用户自己的角色图、场景图或风格参考 |

### 2.2 用户能看到和确认的内容

整个过程中，用户在 **7 个确认点**看到当前阶段的产物，确认后才继续：

| 确认点 | 用户看到什么 | 可以做什么 |
| --- | --- | --- |
| 0 剧情与视觉 | 集数、风格、画面比例的规划 | 调整设定 |
| 1 生成参数 | 将使用的模型与画幅配置 | 更换选择 |
| 2 剧本 | 分集剧本内容 | 修改剧情、重新生成 |
| 3 角色与场景 | 角色形象图、场景图 | 改提示词、重新生成 |
| 4 分镜 | 镜头列表、每个镜头的时长与内容 | 增删镜头、调整顺序 |
| 5 参考图 | 每个镜头的首帧画面 | 改提示词、重新生成 |
| 6 视频片段 | 逐个生成的视频片段 | 对单个片段重做 |

**设计原则**：在产物不可逆或后续成本高的时候停下来确认，可回滚的地方不打断用户。剧本可以改、可以重生成，所以不用逐句确认；角色一旦定稿，后面所有镜头都依赖它，必须停下来；视频片段每一个都在计费，必须逐段把关。

### 2.3 最终产物

| 产物 | 说明 |
| --- | --- |
| 成片视频 | 拼接完成、含音轨、可直接发布 |
| 分集视频 | 多集内容按集拆分 |
| 剧本文件 | 结构化的分集剧本 |
| 角色与场景素材 | 生成的图片及对应提示词 |
| 分镜表 | 镜头号、时长、内容、所用模型 |
| 视频片段 | 全部镜头原片 |

### 2.4 需要长期保留的内容

- 用户创建的每个项目及其全部产物
- 历史生成记录，支持随时回到某个阶段重做

## 3. Agent 的主链路

### 3.1 主链路类型

**分步确认型。** 系统按 6 个阶段依次推进，每个阶段完成后停下等用户确认，用户确认后才进入下一阶段。

```
用户输入创意
    ↓
停点 0：剧情与视觉确认
    ↓
停点 1：生成参数确认
    ↓
剧本生成  ──→  停点 2：剧本确认
    ↓
角色与场景设计  ──→  停点 3：角色场景确认
    ↓
分镜规划  ──→  停点 4：分镜确认
    ↓
参考图生成  ──→  停点 5：参考图确认
    ↓
视频生成  ──→  停点 6：片段确认
    ↓
后期剪辑（自动完成，无需确认）
    ↓
交付成片
```

### 3.2 必须用户确认才能继续的步骤

上表中全部 7 个停点都是强制确认点。**任何跳过确认自动推进的情况都视为缺陷。**

### 3.3 可修改与可继续生成

| 用户想改什么 | 系统行为 |
| --- | --- |
| 某个角色的形象 | 只重新生成该角色及其关联镜头，不影响其他内容 |
| 某个镜头的画面 | 只重做该片段，已确认的片段保持不变 |
| 剧本剧情 | 修改剧本后，后续分镜与片段需要重新生成 |
| 继续往下写 | 在已有分镜基础上续写后续镜头 |

### 3.4 附加能力

除主链路外，提供三条一次成型的简化流程，用户给出素材后后台自动完成，中途不需要确认：

| 流程 | 用途 |
| --- | --- |
| 文艺短视频 | 文字配旁白与配图，生成短视频 |
| 动作迁移 | 把一段动作迁移到指定人物上 |
| 数字人口播 | 生成口播类视频 |

另提供一个临时工作台，用户可以单独使用文生图、图生图、视频生成等单项能力，不需要走完整流程。

## 4. 什么算"生成得好"

### 4.1 好的结果长什么样

一部生成得好的成片应该满足：

1. **故事完整**：有清晰的开头、推进和结尾，不是片段堆砌。
2. **角色一致**：同一个人物在不同镜头里长相、穿着一致。
3. **场景连贯**：同一场景在不同镜头里光线、环境一致。
4. **镜头能接上**：前后镜头的画面衔接自然，不跳。
5. **声画同步**：配音与画面内容对应，字幕准确。
6. **可以直接发布**：不需要用户再拿去做二次剪辑。

### 4.2 可以接受的瑕疵

- 个别画面细节不完美（手部、背景小物件）
- 极短时间内的轻微闪烁
- 字幕偶有断句不理想

### 4.3 不能接受的问题

- 角色在不同镜头里换了长相
- 画面与剧情内容不符
- 成片缺音轨或音画错位
- 生成的画面出现明显错误（多余肢体、文字乱码）

### 4.4 谁来判断

现阶段由产品负责人判断。第一版会准备 5 到 10 条真实生成结果做打分，用打分结果确定正式标准。

### 4.5 衡量指标

| 类别 | 指标 | 目标 |
| --- | --- | --- |
| 完成度 | 从输入创意到拿到成片 | 完整跑通，不中途失败 |
| 效率 | 生成 10 秒成片的耗时 | 实测约 7 分钟（详见预跑报告） |
| 质量 | 用户需要重做的镜头比例 | 待首次真实测试后确定 |
| 成本 | 单条成片的模型花费 | 见第 6 节 |

## 5. 交付阶段与优先级

### 5.1 第一版必须有的

| 优先级 | 内容 |
| --- | --- |
| 必须 | 完整走通 6 个阶段，产出可播放的成片 |
| 必须 | 7 个确认点全部可用，用户能看清产物再决定 |
| 必须 | 单个角色、单个镜头可以单独重做，不用从头再来 |
| 必须 | 能看到每一步花了多少，生成前知道大概要花多少 |
| 必须 | 中途刷新或关闭页面后，回来能接着做 |

### 5.2 之后再做

- 企业团队的多人协作与批量生成
- 用户自有素材库与品牌模板
- 跨项目记住用户的风格偏好

### 5.3 明确不做

| 不做 | 原因 |
| --- | --- |
| 一键出片的黑盒模式 | 用户无法控制结果，不符合核心价值 |
| 多用户账号与权限体系 | 第一版面向单用户使用，无实际用户前不做 |
| **真实支付通道** | **积分与会员的规则已定，但不接微信/支付宝**。需商户号、实名、回调与对账，第一版时间不够 |
| 服务器集群部署 | 单机运行足够支撑第一版验证 |

> **关于计费的说明**：初版 PRD 写的是「计费与支付不做」。现已调整为
> **积分与会员的规则与数据模型要做，真实支付通道不做**。
> 完整规则见《积分与会员模型.md》。理由：积分规则决定扣费点埋在代码的哪里，
> 属于架构决策，越早定越省返工；而支付通道是独立模块，可以后续接入。

### 5.4 截止时间

**两周内**完成第一版。这个时间限制直接决定了上面 5.3 的取舍范围。

## 6. 模型与成本约束

### 6.1 模型厂商

不指定厂商。系统支持多家服务商切换，包括通义、火山方舟、可灵、OpenAI、Gemini、DeepSeek。

视频生成提供三种方式：

| 方式 | 说明 |
| --- | --- |
| 首帧生视频 | 以参考图为起点生成，最稳定 |
| 首尾帧生视频 | 用前后两帧约束，画面衔接更强 |
| 参考图生视频 | 直接使用角色图与场景图，强调一致性 |

### 6.2 成本约束

| 项目 | 约束 |
| --- | --- |
| 单条 10 秒级成片的模型成本上限 | **20 元以内**（实测 ¥10–15，留有余量） |
| 用户是否能看到花费 | 必须能看到，且生成前给出预估 |
| 费用超出预期时 | 暂停并询问用户是否继续 |
| 成本数据可靠性 | 定价必须标来源与核实状态；未核实的模型要明确提示"金额可能不准" |

### 6.3 面向用户的计价方式

用户不直接看到模型成本，而是通过**积分**消费。完整规则见《积分与会员模型.md》。

| 项目 | 结论 |
| --- | --- |
| 计价单位 | 积分。**10 积分 = 1 元成本**，1 积分售价 ¥0.35 |
| 收费倍率 | 1.4（实付 4.90 倍，设计毛利 **79.6%** = 1−1/2.5K²，实测实例毛利 79.7%） |
| 模型档位 | **14 个模型 / 29 个可售档位**（千问 10 + 豆包 4），5 秒片段从 10 积分到 112 积分。完整换算见《积分换算表.md》 |
| 会员价值 | 每月赠送积分 |
| 免费额度 | **注册一次性赠 300 积分**（够跑一次最小闭环：创意 → 看到 5 秒动态画面） |
| 真实支付 | **第一版不接**，积分由管理员发放 |

> **毛利口径更正（2026-09-23）**：此处原写「设计毛利 71.4%」。
> 那是实付倍数被按 `2.5K` 记账的结果；正确是 `2.5K²`（K 在积分数量与
> 积分单价里各出现一次），**实际设计毛利为 79.6%**，落在行业区间 79–82% 内。
> **用户看到的价格一律不变**，只是内部核算口径更正。详见《积分与会员模型.md》§2.4。

**关键事实**：一条 10 秒成片的真实成本约 ¥18.29（含一次视频重做），
因此**成片价格不可能极便宜**。任何"9.9 元做一条视频"的定价都会亏钱。
产品的应对不是降价，而是**让用户先出样片**（用最便宜的特价档，成本 ¥0.75）
确认质量，再决定是否生成其余片段。

### 6.4 成本控制方式

1. 生成前给出预估花费，用户确认后才开始。
2. 单镜头重做，不重跑整条流程。
3. 失败重试有次数上限，不无限重试。

## 7. 数据与非功能要求

### 7.1 数据敏感性

- 用户上传的创意、剧本、素材属于用户内容，不得用于模型训练。
- 生成的成片归用户所有。
- 第一版为单机本地运行，数据不出本机。

### 7.2 用户量预估

第一版为单人使用，用于验证核心体验。

### 7.3 响应时间要求

| 操作 | 可接受时间 |
| --- | --- |
| 界面操作响应 | 1 秒内 |
| 剧本生成 | 2 分钟内 |
| 单张图片生成 | 2 分钟内 |
| 单个视频片段生成 | 5 分钟内 |
| 后期剪辑合成 | 3 分钟内 |

### 7.4 文件限制

- 上传参考图单个不超过 20 MB
- 支持的格式：PNG、JPG、JPEG、WebP

### 7.5 数据必须放国内

**不适用。** 第一版本机运行，数据不出本机，不涉及部署地区问题。

> 若后续上架公网，需重新评估。国内模型服务（通义、火山方舟）本身在国内，
> 数据出境风险来自境外的备选模型（OpenAI、Gemini），届时需按需禁用。

## 9. 需求确认清单（已全部关闭）

本清单已全部确认，确认日期 2026-09-22。确认后进入开发。

| 编号 | 问题 | 最终确认结论 | 依据 |
| --- | --- | --- | --- |
| Q1 | 第一版的成片篇幅是多少 | **1 集、10 秒级短片** | 产品负责人确认。首版目标是验证流程，不追求时长 |
| Q2 | 单条成片的模型成本上限 | **20 元以内** | 真实预跑实测 ¥10–15，留有余量 |
| Q3 | 什么画面错误绝对不能接受 | **角色长相不一致、画面与剧情不符、画面明显错误** | 产品负责人确认，已写入第 4.3 节 |
| Q4 | 生成时是否需要引入用户自己的素材 | **不需要**。第一版只用系统生成的素材 | 引入素材需额外开发上传与管理，超出首版范围 |
| Q5 | 同一个项目是否可以多人同时编辑 | **不可以**。第一版单人使用 | 多人协作需账号与权限体系，范围会显著扩大 |

### 确认结论带来的实现约束

| 结论 | 已落实为 |
| --- | --- |
| Q1 篇幅 | 默认 1 集；实测成片 10.21 秒 |
| Q2 成本上限 | 定价注册表 + 生成前报价（后端已就绪） |
| Q3 画面底线 | VLM 自检 + 不合格自动重做，已实测生效 |
| Q4 不引入素材 | 首版不做素材上传与管理 |
| Q5 单人使用 | 不做账号体系；但**上架公网前必须补**（见《部署安全.md》） |

### 需要留意的一处变化

真实预跑后发现：**单集剧本只拆出 2 个镜头，成片 10.21 秒**，而非最初设想的 6–8 个镜头、
约 1 分钟。原因是内容长度问题，不是功能缺陷。产品负责人已确认接受 10 秒现状。

若要达到 1 分钟成片，需加长剧本或增加集数——这属于内容长度决策，不是功能改动。
