## 四、环境坑（重要，会重复遇到）

### 坑一：macOS 隔离属性阻止原生模块加载

**症状**：`library load disallowed by system policy` 或 `Cannot find native binding`

**原因**：`node_modules` 里的原生二进制带 `com.apple.quarantine`，macOS 拒绝加载 ad-hoc 签名的二进制。

**修复**：`xattr -dr com.apple.quarantine .`

### 坑二：Turbopack 无法解析 lightningcss

**症状**：`Cannot find module '../lightningcss.darwin-arm64.node'`，但用纯 Node 测试 `require('lightningcss-darwin-arm64')` 是成功的。

**原因**：此环境下 Turbopack 的模块解析缺陷（`process.versions.electron` 存在，npm 经由 Electron 运行）。

**绕过**：用 Webpack 模式，`npm run dev -- --webpack`，已验证 6 个路由全部正常。

### 坑三：系统 Python 版本不足

系统只有 `/usr/bin/python3` 3.9.6，项目要求 >= 3.10。必须用外接盘的 Python 3.12，不要用系统 Python 建虚拟环境。

## 八、成本记账的三个必知事项

**1. 客户端不要自己算钱，只报用量。**
五个客户端（`llm_dashscope` / `vlm_dashscope` / `video_seedance` /
`video_dashscope` / `image_client`）各自调用 `report_usage(Usage(...))`，
由定价层决定这对应哪一档、多少钱。改价目表不该动客户端。

**2. 线程池里必须用 `submit_with_cost_context`，不能用 `executor.submit`。**
Python 的 `ThreadPoolExecutor` **不复制** contextvars。漏用的后果是
**静默丢账**——不报错、不写日志，只是账少了。有一条单测静态扫描源码禁止裸 submit。

**3. 报 per_second 用量时必须带上分辨率与音轨。**
`wan2.6-i2v-flash` 720P 无声 ¥0.15/秒、1080P 带音 ¥0.50/秒，差 3.3 倍。
只报秒数会把 1080P 记成 720P 的价。

**实测标定过的 tokens 表**（`pricing.SEEDANCE_EFFECTIVE_PIXELS`）：

| 分辨率 | 有效像素 | 依据 |
| --- | ---: | --- |
| 480P | 428,544 | 实测反推（864×496，**非名义 864×480**） |
| 720P | 921,600 | 两个样本精确复现（1280×720） |
| 1080P | — | **未实测，报价返回 None，不猜** |

公式：`tokens = 有效像素 × (秒 × 24 + 1) ÷ 1024`
——注意那个 `+1` 帧，所以 **10 秒不是 5 秒的两倍**。

## 九、积分扣费（已实现，改动前先读这段）

| 概念 | 说明 | 位置 |
| --- | --- | --- |
| 预扣 | 阶段开始前占住一笔，余额不足**直接拦住阶段** | `orchestrator._reserve_stage_credits` |
| 结算 | 阶段结束按 `cost_store` 的**真实金额**换算成积分结算 | `orchestrator._settle_stage_credits` |
| 退回 | 仅用于"确认没有产生任何成本"的情况 | `credits_store.release` |
| 幂等键 | `ref = "{session_id}:{stage}"`，重试/续跑/连点都不会重复扣费 | `credits_store.reserve` |
| 对账 | `sum(流水) == balance`，每笔记 `balance_after` | `credits_store.verify` |

**三条别踩的线**：
1. **失败也要结算到实际用量**，不能全额退回——跑掉的那几次调用是真花了钱的
2. **`total_consumed = 获得 − 可用 − 冻结`**，不是"消费流水之和"
3. **发积分接口只能在本机模式可用**（它没有鉴权）
