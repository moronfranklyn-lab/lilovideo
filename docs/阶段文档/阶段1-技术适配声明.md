## 一、我对需求的理解

### 产品是什么

**Lilovideo**：从一句创意到一部成片的 AI 视频生产系统。

用户给一句话，系统按 6 个阶段产出成片：

```
剧本策划 → 角色/场景设计 → 分镜规划 → 参考图生成 → 视频生成 → 后期剪辑
```

每个阶段有专职 Agent，前一阶段产物决定后一阶段输入，**关键节点停下来等用户确认**。

### 我认为的核心价值

不是"文生视频"，而是**可控的生产流程**：

| 普通文生视频工具 | 本产品 |
| --- | --- |
| 生成一个片段 | 产出完整成片 |
| 角色跨镜头不一致 | 角色定稿后所有镜头共用 |
| 改一处要全部重来 | 单镜头重做，不动其余 |
| 黑盒计费 | 生成前报价、过程可见 |

### 我认为的取舍立场

**只在"产物不可逆"或"边际成本高"的地方停下问用户。** 剧本可改所以不停；角色定稿必须停（后面全依赖它）；视频片段必须停（每秒都在计费）。

### 一句话的验收标准

**能用、能演示**：一条命令起服务，一次真实生成能产出可播放的成片。

## 二、有没有多出你没要求的花费、平台、范围

### 2.1 花费：有，但已实测并给出上限

**这是本节最重要的一条。**

产品需要**两个平台**，不是最初设想的一个。原因是实测发现的硬约束：

| 平台 | 提供什么 | 为什么不能少 |
| --- | --- | --- |
| **火山方舟 ARK** | 图像（Seedream）+ 视频（Seedance） | 视频模型是你指定的 Seedance |
| **通义 DashScope** | 语言模型 + 视觉模型 | **ARK 只有图像和视频模型，没有 LLM 和 VLM** |

我核对了 ARK 全部 22 个模型：只有 8 个图像 + 14 个视频，**没有任何语言或视觉模型**。而主流程要写剧本（LLM）、要评估角色图（VLM）。所以必须有第二个平台。

**实测花费**（真实预跑一次，完整 6 阶段）：

| 项目 | 数值 |
| --- | --- |
| 图像生成调用 | 25 次 |
| 视频片段 | 2 个 × 5 秒 |
| 成片 | 10.21 秒 |
| **预估花费** | **¥10–15** |

> 这是按公开单价估算，不是账单数据。精确金额请在两个平台的费用中心查看。

**建议的成本上限**：单条 10 秒级成片 **¥20 以内**。

| 成本展示前端 | 后端已就绪 | **不影响流程跑通**，但影响"成本可见"这一产品主张 |
| 样片模式前端 | 后端已就绪 | **不影响**，但省成本的能力用户用不到 |

### 未暂缓但已加固的一项（重要）

**部署安全。** 审计时发现底座的配置接口存在真实风险：

- `PUT /api/config` 无任何鉴权
- 该接口接受任意 `base_url`，**攻击者可把接口地址指向自己的服务器，之后所有模型请求连同 API Key 都会发到那里**

由于你明确表示会考虑上架公网，已加固两道防线：

1. **环境变量优先**：线上密钥只放服务端环境变量，且**不落回可写文件**
2. **公网模式封死配置写接口**：按监听地址自动判定，监听 `0.0.0.0` 时 `PUT /api/config` 返回 403

实测结果：公网模式下 `PUT /api/config` → **HTTP 403**，攻击者的 `base_url` **未被写入**。

> **但这只挡住了"密钥被窃取"，不挡"额度被刷光"。** 账号鉴权、配额限流仍缺失，
> 上架公网前必须补。这一条已写入《部署安全.md》的"仍未覆盖的范围"。
